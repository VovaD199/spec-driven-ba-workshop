## Крок 1. Власний репозиторій з шаблону (≈10 хв)
1. Увійдіть на https://github.com.
2. Відкрийте шаблон https://github.com/VovaD199/spec-driven-ba-workshop-template і натисніть **Use this template → Create a new repository**.
3. Назва: `sdd-workshop-<ваше-імʼя>` латиницею. Видимість: **Public** (ментор має бачити PR). Не кладіть у репозиторій паролі й токени. **Create repository**.

**ПЕРЕВІРТЕ:** у вашому репозиторії є `README.md`, `package.json`, папка `app/`.

## Крок 2. Код на комп'ютер (≈10 хв)
Відкрийте термінал. **КОПІЮЙТЕ** (замініть `<логін>` та `<імʼя>`):

macOS / Linux:
```bash
mkdir -p ~/Projects && cd ~/Projects
git clone https://github.com/<логін>/sdd-workshop-<імʼя>.git
cd sdd-workshop-<імʼя>
```
Windows PowerShell (клонуйте ближче до кореня диска, шляхи довгі):
```powershell
mkdir C:\Projects -Force; cd C:\Projects
git clone https://github.com/<логін>/sdd-workshop-<імʼя>.git
cd sdd-workshop-<імʼя>
```

**ПЕРЕВІРТЕ:** `git status` каже `On branch main`.

**ЯКЩО НЕ ВИЙШЛО:**
- Просить логін/пароль або `Authentication failed`: пароль не діє. Виконайте `gh auth login` (див. [День 0, розділ 2](../day-0/day-0-prepare.md)).
- Довгі шляхи (Windows): `git config --global core.longpaths true`.
- `SSL certificate problem` (Windows): `git config --global http.sslBackend schannel`, потім повторіть.
- Git не працює зовсім: на сторінці репозиторію **Code → Download ZIP**, розпакуйте й працюйте з розпакованою папкою.

## Крок 3. Відкриття проєкту в Cursor (≈10 хв)
1. **File → Open Folder** → папка проєкту. На «Trust this workspace?» оберіть **Yes, I trust the authors**.
2. Термінал у Cursor: меню **Terminal → New Terminal** (або `Ctrl+Shift+P` / `Cmd+Shift+P`, команда `Terminal: Create New Terminal`).
3. Модель: оберіть найдешевшу, щоб зберегти ліміт безкоштовного плану: [cursor-model-tips](../setup/cursor-model-tips.md).

**ПЕРЕВІРТЕ:** унизу є термінал, шлях веде до папки проєкту; ліворуч дерево файлів.

> **Чат агента** відкривається панеллю справа. Гарячі клавіші залежать від версії Cursor (зазвичай `Ctrl+L` / `Cmd+L`); перевірте в меню або в [документації Cursor](https://docs.cursor.com). `<ментор уточнює актуальну клавішу на занятті>`.

## Крок 4. Запуск застосунку (≈20 хв)
У терміналі Cursor по черзі:

```bash
cp .env.example .env         # Windows PowerShell: Copy-Item .env.example .env
npm ci
npm run dev
```
- `.env` це локальні налаштування; у Git не потрапляє (він у `.gitignore`). Значень за замовчуванням достатньо.
- `npm ci` встановлює бібліотеки точно тих версій, що записані в `package-lock.json`, і **не змінює** цей файл (на відміну від `npm install`, який інколи його переписує: тоді він потрапляє в зміни, а комітити його не треба). Перший раз триває до кількох хвилин, у проєкті з'явиться `node_modules/`. Попередження (warning) від npm нормальні, помилки (error) ні.
- `npm run dev` запускає локальний сервер і **займає це вікно термінала**. Для інших команд відкрийте **другий термінал**: кнопка `+` у панелі терміналу. Зупинити сервер: `Ctrl+C`.

Відкрийте http://localhost:3000/en у браузері.

**ПЕРЕВІРТЕ:** відкривається сайт Фонду Лятошинського. Перегляньте «Про фонд» і «Контакти»: які розділи справжні, які заглушки?

**ЯКЩО НЕ ВИЙШЛО:**
- Порт 3000 зайнятий: використайте адресу, яку покаже термінал.
- `npm ci` падає: `node -v` має бути 22+; повторіть без VPN. Якщо npm пише, що `package.json` і `package-lock.json` не синхронізовані, виконайте `npm install` і повідомте ментора; файл `package-lock.json` у такому разі **не комітьте** (`git restore package-lock.json`).
- `running scripts is disabled` (Windows): `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.
- Сторінка порожня після змін: `Ctrl+C` і `npm run dev` знову.
- Не вийшло за 20 хв: ментор покаже запущений застосунок на екрані, ви продовжуєте кроки без нього (крок 5 і далі потребують лише файлів).

База даних у пам'яті й наповнюється демо-даними при кожному запуску, зламати остаточно нічого не можна.

**Що в проєкті (скорочено):** `package.json` (залежності й команди), `app/` (сторінки, API, сервіси), `i18n/messages/` (тексти uk/en), `scripts/` (демо-дані), `node_modules/` (бібліотеки, з'являється після `npm ci`).

> Python-розробникам: `npm ci` ≈ `pip install -r requirements.txt` (точні версії з lock-файлу), `package.json` ≈ `requirements.txt`, `node_modules/` ≈ `.venv/`, `npm run dev` ≈ `python main.py`.

## Крок 5. Знайомство з проєктом через агента (≈15 хв)
Відкрийте новий чат агента.

**У ЧАТ CURSOR:**

## Крок 7. Постійні інструкції для агента: `AGENTS.md` (≈30 хв)
`AGENTS.md` у корені проєкту Cursor читає автоматично. Аналітик не пише код, але пише інструкції.

**У ЧАТ CURSOR:**
```text
На основі того, що ти знаєш про цей проєкт, напиши стартовий файл AGENTS.md
для нового члена команди, який є бізнес-аналітиком.

Включи:
- однопараграфовий опис проєкту
- основні сторінки та їх бізнес-призначення (таблицею)
- конвенції: TypeScript, без default export, українська (uk) як основна мова
- примітку, що це навчальний репозиторій і БД скидається при кожному запуску
```
Перегляньте результат, **виправте мінімум дві неточності** (це ваша аналітична частина) і збережіть як `AGENTS.md` у корені. Конвенції («TypeScript, без default export») підказка для агента, а не бізнес-вимога; залиште їх, але розрізняйте такі речі.

**ПЕРЕВІРТЕ:** відкрийте **новий** чат і запитайте: «Що це за проєкт? Відповідай так, ніби я щойно долучився до команди.» Агент має відповісти термінами з вашого `AGENTS.md`. Якщо ні: перезапустіть Cursor.

*Необов'язково (швидка доріжка, див. S1):* правило для документів у `.cursor/rules/`.

## Крок 8. Діаграма архітектури (Mermaid) (≈20 хв)
**У ЧАТ CURSOR:**
```text
Вивчи структуру проєкту, зокрема app/[lang]/, app/api/, app/services/,
app/infrastructure/ та app/di/.

Згенеруй Mermaid-діаграму flowchart TD, що показує:
- основні сторінки
- API-маршрути, які вони викликають
- сервіси, які використовують ці маршрути
- інфраструктуру (моделі/репозиторії БД), від якої залежать сервіси

Підписуй вузли справжніми назвами папок або файлів.

Створи файл docs/architecture.md (папку docs створи, якщо її немає) і запиши в нього:
- короткий вступ (2–3 речення) про те, що показує діаграма;
- діаграму в блоці коду з міткою mermaid.
```
**ПЕРЕВІРТЕ:** файл `docs/architecture.md` існує (якщо ні: «Збережи діаграму у файл docs/architecture.md»). Перегляд: `Ctrl+Shift+V` / `Cmd+Shift+V` у Cursor або https://mermaid.live. Діаграма не рендериться: перевірте, що блок починається з ```` ```mermaid ````, або вставте код на mermaid.live.

**Обговорення:** чого на діаграмі немає? Де працюють ваші знання про бізнес?

## Крок 9. Здача: Pull Request (≈25 хв)
Усі команди виконуйте в терміналі в папці проєкту (якщо працює сервер, відкрийте другий термінал).

```bash
git checkout -b day-1
git status
```
`git status` має показати `AGENTS.md` і `docs/architecture.md` (як нові). Якщо ні, поверніться до кроків 7-8.

```bash
git add AGENTS.md
git add docs/architecture.md
git status
git commit -m "docs: add AGENTS.md and architecture diagram (day 1)"
git push -u origin day-1
```
Автентифікація: див. День 0, розділ 2. Потім на GitHub натисніть **Compare & pull request → Create pull request** (з `day-1` у `main` **вашого** репозиторію). Надішліть ментору посилання на PR (канал: `<вказує ментор>`).

> Файл `docs/questions.md` ви додасте в **цей самий PR** у кроці 10, тому не зливайте PR, поки не виконаєте крок 10 і не отримаєте відгук ментора.

**Вимоги до PR:**
- з гілки `day-1` у `main` вашого репозиторію (не в шаблон), репозиторій публічний;
- назва: `День 1: <коротко, що зроблено>`;
- опис 2-4 речення: що зроблено, що було складним, що лишилось незрозумілим;
- у **Files changed** лише файли дня; ніяких `.env`, `node_modules`, `.cursor/mcp.json`, токенів;
- після відгуку ментора натисніть **Merge pull request**, щоб наступного дня почати з актуального `main`. **Не зливайте до відгуку ментора.**

**ПЕРЕВІРТЕ перед комітом:** `git status` не показує `.env`, `node_modules`. Якщо в змінених файлах є `package-lock.json`, не додавайте його: `git restore package-lock.json`.

**ЯКЩО НЕ ВИЙШЛО (git push):** помилка автентифікації → `gh auth login`; `src refspec day-1 does not match` → ви не створили гілку чи нічого не закомітили: `git checkout -b day-1`, потім `git add` і `git commit`. Після 20 хв: надішліть ментору файли (скріншот / zip), це зараховується як здача з позначкою «без PR».

## Крок 10. Аналітичне завершення: питання до замовника (≈15 хв)
Ви вже знаєте продукт з боку коду й браузера. Тепер подивіться на нього очима аналітика.

**У ЧАТ CURSOR:**
```text
Прочитай AGENTS.md і docs/architecture.md. Склади список із 5 питань до замовника
(Фонд Лятошинського), без відповідей на них у коді. Для кожного питання вкажи:
навіщо це питання (яке рішення від відповіді залежить) і хто на нього може відповісти.
```
Відредагуйте список (видаліть із відповіді рядки на кшталт «Якщо потрібно, можу оформити…»: це текст чату, а не питання) і збережіть у файлі `docs/questions.md`.

**Додайте файл у той самий Pull Request** (він ще відкритий: зливати його можна лише після відгуку ментора). У терміналі, на гілці `day-1`:
```bash
git status
git add docs/questions.md
git commit -m "docs: add questions for the client (day 1)"
git push
```
PR оновиться сам: у вкладці **Files changed** з'явиться `docs/questions.md`. Нічого більше відкривати не треба. Напишіть у коментарі до PR: «Додано питання до замовника (крок 10)».

**ЯКЩО PR уже злито** (наприклад, ви натиснули **Merge** раніше): створіть нову гілку й другий PR:
```bash
git checkout main
git pull
git checkout -b day-1-questions
git add docs/questions.md
git commit -m "docs: add questions for the client (day 1)"
git push -u origin day-1-questions
```
Потім **Compare & pull request** з `day-1-questions` у `main` вашого репозиторію й надішліть ментору посилання.

**Критерій якості:** питання відкриті («чому», «хто», «що станеться, якщо…»), без підказки відповіді; хоча б одне про приватність даних відвідувачів. Цей документ знадобиться в Дні 2.

## Критерії перевірки (ментору)
1. `AGENTS.md` і діаграма в PR, відповідають реальному проєкту (немає вигаданих сторінок).
2. Видно власну правку (не лише AI-текст), ≥2 виправлення.
3. Немає службових файлів і секретів.
4. `docs/questions.md`: ≥4 відкриті питання з «навіщо» і «хто».

## Швидка доріжка: стретч-завдання
- **S1.** Створіть правило Cursor у `.cursor/rules/` для `docs/**/*.md` (одна тема на файл, заголовок із поясненням «навіщо»). *Критерій:* новий чат дотримується правила; ви виправили згенероване.
- **S2.** Попросіть агента знайти в коді 3 бізнес-правила, яких немає в README, і для кожного вкажіть файл. Перевірте вручну. *Критерій:* 3 правила з посиланнями на файли, підтверджені вами.
- **S3.** Додайте до `docs/architecture.md` другу діаграму (послідовність: що відбувається, коли відвідувач надсилає форму контактів). *Критерій:* діаграма збігається з реальною поведінкою у браузері.
