# Частина A. Sandbox-PoC

## A1. Що таке PoC для аналітика
PoC (proof of concept) для BA це **одноразовий експеримент, що відповідає на одне питання**: «Якщо правило працювало б так, чи поводилася б система так, як очікують стейкхолдери?»

| BA PoC… | BA PoC НЕ… |
|---|---|
| Перевіряє одну гіпотезу | Є реалізацією фічі |
| Змінює код лише тимчасово | Потрапляє в `main` |
| Дає докази (diff, скріншот, результат тестів) | Замінює оцінку розробників |
| Виявляє невідоме до refinement | Відповідає «яке рішення технічно правильне» |

Результат дня це **документи**, а не код: код ми скасуємо, докази лишаться. PoC недоречний, якщо потрібен справжній API-виклик, реальні дані чи зміна понад 2-3 файли: позначте «потрібен розробник».

**Наша гіпотеза (з Дня 2):** *«Якщо зробити телефон обов'язковим і зменшити мінімальну довжину повідомлення, система поводитиметься узгоджено на клієнті й сервері.»* Ви перевірите її двома пробами.

## A3. Проба 1: обов'язковий телефон (30 хв)
**Сценарій.** Замовник хоче зробити телефон обов'язковим (ваш RULE з Дня 2). Подивимось, що це зачепить.

**Спершу своє:** у `docs/poc-notes.md` запишіть, які місця в коді, на вашу думку, треба змінити (використайте таблицю правил і аналіз впливу з Дня 2).

**У ЧАТ CURSOR:**
```text
Знайди всі місця, де телефон у формі контактів оголошено необов'язковим (клієнт, сервер,
тести, переклади). Покажи файл і рядок для кожного. Потім покажи diff, який робить
телефон обов'язковим у всіх цих місцях. Поки не застосовуй.
```
Перегляньте diff: чи охопив він і клієнтську форму (`ContactForm.tsx`), і серверний валідатор (`validateContactData.ts`)? Якщо так, застосуйте:
```text
Застосуй зміну.
```
**Перевірка в браузері.** Перезапустіть сервер (`Ctrl+C`, `npm run dev`), відкрийте http://localhost:3000/en/contacts і спробуйте відправити форму **без телефону**. Занотуйте: що показала форма? Чи є позначка «обов'язкове»?

**Перевірка тестами** (у другому терміналі, займає секунди):
```bash
npx jest app/lib/utils/validateContactData.test.ts --coverage=false
```
Занотуйте, які тести **червоні** і чому. Червоний тест тут не помилка, а знахідка: він показує, яку поведінку замовник змінює.

**Запишіть у `docs/poc-notes.md`** розділ «Проба 1». Не вставляйте відповіді з чату: лише те, що самі бачили.

> Безпечна зміна для пісочниці: зачіпає ≤3 файлів, скасовується (`git restore`), не викликає зовнішніх API і не пише у спільну БД. Погані кандидати: автентифікація, платежі.

## A4. Проба 2: мінімальна довжина повідомлення (25 хв)
**Сценарій.** Чи можна знизити мінімум повідомлення з 10 до 5 символів?
```text
Знайди, де перевіряється мінімальна довжина повідомлення (клієнт, сервер, тести, переклади).
Покажи поточне значення, файл і рядок. Потім покажи diff зміни мінімуму до 5. Поки не застосовуй.
```
**Спершу своє:** скільки місць ви очікуєте? Потім порівняйте. Запитайте: «Чи є ще місця, які ти пропустив?»

<details><summary>Орієнтир (відкривайте після своєї спроби)</summary>

Значення живе щонайменше в трьох місцях: `MESSAGE_MIN_LENGTH` у `app/constants/validation.ts` (сервер), число `.min(...)` у `ContactForm.tsx` (клієнт) і текст помилки «at least 10 characters» в `i18n/messages` (en та uk). Якщо змінити лише константу, API прийматиме 5 символів, а форма й далі вимагатиме 10.
</details>

Застосуйте зміну **в усіх** знайдених місцях. Перевірте в браузері на `/en/contacts` повідомлення з 6 символів. Запустіть тести:
```bash
npx jest app/lib/utils --coverage=false
```
**Запишіть** у розділ «Проба 2»: що змінили, що побачили, які тести червоні.

**Обговорення:** це перший крок замкненого циклу *вимога → код → тест*: зміна правила в одному місці породила червоні тести в іншому. Скільки місць треба змінити, щоб змінити правило? Чи це знахідка для специфікації?

## A6. Чекліст «доведено / не доведено / потрібен розробник» (15 хв)
**Правило:** «доведено» лише те, що ви **самі бачили** й записали в `docs/poc-notes.md`.
```text
На основі git diff моєї гілки (виконай команду сам) і моїх нотаток @docs/poc-notes.md
допоможи заповнити чекліст. Для кожної зміни:
1. Доведено: лише записане мною як побачене.
2. Не доведено: правдоподібне, але без спостереження в нотатках.
3. Потрібен розробник: питання, на які не відповісти з коду самостійно.
Якщо спостереження немає, пиши «не зафіксовано», а не припускай.
```
Рядки «Потрібен розробник» можна лишити відкритими: це чесний стан. Приклади питань: чи ця зміна узгоджена з AC з Дня 2? Яке значення мінімуму правильне за вимогами замовника?

## A8. Здача PoC: зберегти документи, скасувати код (10 хв)
Одна гілка, без переходів між гілками. **Порядок важливий:** спершу комітимо документи, потім скасовуємо код.
```bash
git add docs/poc-notes.md
git add docs/poc-summary-<дата>.md
git commit -m "docs: add PoC notes and summary (day 3)"
git restore .
git status
```
- `git restore .` скасовує **незакомічені** зміни відстежуваних файлів (код PoC). Документи вже закомічені, їм нічого не буде. Якщо ви ще не закомітили документи, **не запускайте** `git restore .` (нові незастейджені файли він не видаляє, але правки в уже відстежуваних файлах втратите).
- **ПЕРЕВІРТЕ:** `git status` каже `nothing to commit, working tree clean`; `git diff main --stat` показує лише файли в `docs/`.

```bash
git push -u origin day-3
```
**ЯКЩО НЕ ВИЙШЛО:** скопіюйте документи в безпечне місце поза проєктом, скиньте стан (`git restore .`, `git checkout main`), створіть `day-3` заново й покладіть документи назад.

> Ніколи не пушите PoC-код у спільний репозиторій без обговорення. Цінність у тому, що PoC довів, а не в коді.

**У FIGMA MAKE:**
```text

(the Liatoshynsky Foundation).

Requirements:
- Fields: Name, Email, Phone number (required, international format starting with +),
  Message, and an optional file attachment (PDF only, max 5 MB).
```

Не перериваючи, дочекайтеся результату. Генеруйте **один раз**, уточнюйте мінімум (кредити обмежені). - **S2. Підпис кнопки.** «Support the Foundation» → «Become a patron» на `/en/support-us`; знайдіть **усі** ключі в `i18n/messages` (en та uk). *Критерій:* список ключів і чи треба міняти український переклад.
- **S3. Feature flags.** Чи є в коді перемикачі за змінними середовища? Опишіть, де б ви додали простий булевий флаг для сторінки. *Критерій:* список файлів, яких він торкнеться, з підтвердженням вручну.

Усі стретч-зміни теж скасовуються `git restore .` до здачі.
